# PI-Owned Catalog — Migration Design (Phase 3–4)

**Status:** Additive / shadow executed (2026-09-19). **Production cutover not approved.**  
**Companion:** `reports/architecture/pi_catalog_shadow_stop_report.md`  
**Audit:** `reports/architecture/pi_independence_audit.md`  
**Date:** 2026-09-19

---

## Goals

1. PI owns a canonical paper catalog (`paper_intelligence.papers`).
2. Pipeline eligibility uses PI stage results / current projection — never Radar `status`.
3. Preserve existing identities, enrichment, LLM costs, caches, versions, provenance.
4. Additive migrations first; no big-bang rewrite; no silent historical re-score.

---

## Proposed schema

### `paper_intelligence.papers`

| Column | Type | Notes |
|---|---|---|
| `paper_id` | `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | Stable PI id |
| `legacy_content_item_id` | `BIGINT UNIQUE` | Crosswalk to Radar `content_items.id` |
| `arxiv_id` | `TEXT` | Canonical arXiv id without version suffix when possible |
| `doi` | `TEXT` | Optional |
| `source` | `TEXT NOT NULL` | e.g. `arxiv_oai`, `manual` |
| `source_external_id` | `TEXT` | Source-native id |
| `canonical_url` | `TEXT` | Prefer arXiv abs URL |
| `title` | `TEXT NOT NULL` | |
| `abstract` | `TEXT` | Or pointer if later externalized |
| `summary` | `TEXT` | Ingest summary if distinct |
| `categories` | `JSONB NOT NULL DEFAULT '[]'` | |
| `authors_raw` | `JSONB` | |
| `authors_structured` | `JSONB` | OAI structured authors when present |
| `affiliation_text` | `TEXT` | Captured evidence |
| `extracted_emails` | `JSONB` | |
| `published_at` | `TIMESTAMPTZ` | Source publication/submission date |
| `source_updated_at` | `TIMESTAMPTZ` | Upstream update timestamp |
| `ingested_at` | `TIMESTAMPTZ NOT NULL DEFAULT NOW()` | PI ingest time (distinct from published_at) |
| `raw_metadata` | `JSONB NOT NULL DEFAULT '{}'` | Provenance blob |
| `created_at` / `modified_at` | `TIMESTAMPTZ` | |

**Uniqueness / dedupe**

1. Unique `(source, source_external_id)` where external id present.
2. Unique `arxiv_id` where present (normalize: strip version `vN`).
3. Unique `doi` where present (normalized lowercase).
4. Unique `legacy_content_item_id`.
5. Rediscovery (HF Daily Papers, re-harvest) **updates** the same row keyed by arXiv id — never inserts a duplicate.

**Not a funnel status column.** Processing state lives in:

- append-only `paper_classification_results` (versioned)
- `item_stage_runs` / `stage_runs` / `pipeline_runs`
- `paper_intelligence_current` projection (`quality_status`, affiliation statuses, scores)

Partial success / retry / skip / fail remain per-stage, independently.

### Crosswalk

`paper_intelligence.paper_identity_map` (optional if columns on `papers` suffice):

- `paper_id`
- `system` (`research_radar` | `arxiv` | `doi` | `hf`)
- `external_id`
- unique `(system, external_id)`

### Checkpoints / rejects

- `paper_intelligence.ingest_checkpoints` (replace Radar `backfill_checkpoints` for PI runs)
- `paper_intelligence.s3_archives` (replace Radar `s3_archives` for PI rejects)

### Relevance results (PI-owned)

`paper_intelligence.paper_relevance_results` append-only:

- `paper_id`, score, decision (`keep`/`reject`), version, reason, run_id, created_at

Paid stage pools then select `keep` + missing stage results — **no Radar status**.

## Migration steps (additive)

### Step A — DDL only

1. Create `papers`, identity map, relevance results, ingest checkpoints, s3 archives.
2. Add nullable `paper_id` columns alongside `content_item_id` on PI child tables
   **or** plan a later rename after dual-write.

Prefer: keep `content_item_id` as the physical FK value during transition if
`paper_id = legacy_content_item_id` is validated safe (same bigint space).

**ID reuse rule:** If every PI `content_item_id` equals Radar `content_items.id` and
no collisions exist, set `papers.paper_id = legacy_content_item_id` explicitly
(identity override) to avoid rewriting FKs. Validate before choosing this.

### Step B — Backfill

1. Insert into `papers` from Radar `content_items` ⋈ `paper_metadata` for all ids
   referenced by any PI table (and optionally full shared catalog).
2. Validate: counts, unique arxiv_id, orphan PI rows, null published_at rates.
3. Do **not** delete Radar rows.

### Step C — Dual-write ingest

1. PI ingest writes `papers` first; optionally still upserts Radar for compatibility
   behind a flag `PI_WRITE_RADAR_COMPAT=1` (default on initially).
2. New papers can exist in PI without Radar when flag off (independence proof).

### Step D — Readers cutover

1. `fetch_papers`, affiliation fetch, HF lookup, adjudication window, reports → `papers`.
2. Quality routing already PI-screen-based (Phase 2).
3. Compatibility shims remain in `db/results.py` behind clear comments.

### Step E — Stop Radar status dependency entirely

1. PI relevance writes `paper_relevance_results` only.
2. Remove `PI_ELIGIBLE_STATUSES` usage from selectors.
3. Drop optional Radar compat writes.

### Step F — FK migration

1. Add FKs to `papers(paper_id)`.
2. Remove `ON DELETE CASCADE` to Radar.
3. Keep Radar tables untouched.

---

## Rollback

1. Feature flags: `PI_USE_PAPERS_CATALOG`, `PI_WRITE_RADAR_COMPAT`.
2. DDL is additive — rollback = flip flags; do not drop `papers` until reconciled.
3. If dual-write diverges: reconcile using `legacy_content_item_id` + arxiv_id uniqueness report.
4. Never CASCADE-delete Radar to “clean up”.

---

## Independence checklist (Phase 6 — after cutover)

1. Ingest arXiv paper without creating Radar row (compat flag off).
2. Complete pipeline without reading Radar status.
3. Change Radar status → PI eligibility unchanged.
4. Reports/editorial use PI catalog.
5. Historical enrichment reachable via `paper_id` / legacy map.
6. No duplicate arXiv papers.
7. Stage reruns version-aware / idempotent.
8. Failed stage resume without full restart.

---

## Explicit non-goals for this design approval

- No bulk paid re-score of the corpus.
- No deletion of Radar tables.
- No commit/deploy until human review of Phase 2 + this design.
